# HitbotOS Store 小程序版落地分析

> 日期：2026-06-08
> 目标：在保留 PC/H5 商城核心能力的前提下，设计并落地微信小程序版。重点不是把 PC 页面缩小，而是把 B2B 采购、项目 BOM、询价和订单动作改造成适合手机触控、微信登录和短任务场景的体验。

---

## 1. 结论

小程序版建议定位为 **HITBOT 产品选型与采购工作台**，而不是“PC 商城的移动镜像”。

PC 当前主线是：商品列表/详情 -> 项目 BOM 购物车 -> 结算 -> 企业账号 -> 订单/审批/付款/发票。小程序应保留这些业务语义，但入口和交互要重排：

1. **商品浏览更轻**：搜索、分类、筛选、详情和加购必须好用，列表页不堆 PC 侧筛选面板。
2. **购物车改名为方案清单/BOM**：突出项目语境、OS 来源、标准件/定制件/参考件，而不是普通电商购物车。
3. **结算拆成移动短流程**：工程师只提交给采购；采购/管理员才处理地址、发票、审批和付款。
4. **订单中心先做行动队列**：小程序最适合“待审批、待付款、待确认、待报价”的轻操作。
5. **范围保持克制**：小程序不承接在线体验 OS，也不做管理后台；复杂企业配置优先留给 PC。

## 2. 当前 PC 功能映射

| PC/H5 模块 | 小程序落地方式 | 优先级 | 说明 |
|---|---|---:|---|
| 商品列表 | 原生产品页，顶部搜索 + 横向分类 + 筛选底部抽屉 | P0 | 适合手机单列卡片，减少首屏遮挡 |
| 商品详情 | 原生详情页，图片/价格/规格/兼容附件/底部 CTA | P0 | CTA 固定底部：加入方案、询价、联系销售 |
| 购物车 | 改为“方案清单”，按项目显示 BOM | P0 | 保留 `projectId/source/selected/sellable/quoteRequired/syncStatus` 语义 |
| 结算页 | 分角色短流程 | P0 | 工程师提交采购；采购/管理员提交订单或询价 |
| 企业登录 | 微信登录 + 企业账号绑定 | P0 | 不能沿用 PC 的 mock 用户选择 |
| 订单列表 | 订单行动队列 + 订单详情 | P0 | 待审批/待付款/待报价优先 |
| 个人中心 | 我的企业、地址、发票、成员入口 | P1 | 管理项首版收敛，复杂设置可跳 H5/PC |
| 审批配置/成员权限 | 小程序只做轻管理或只读 | P2 | 完整配置建议留 PC |
| 在线体验 OS | 不进入小程序范围 | 不做 | 由官网/H5/PC 体验链路承接 |
| 管理后台 | 不进入小程序范围 | 不做 | 与当前 PRD 一致 |

## 3. 小程序信息架构

推荐四个 Tab：

| Tab | 名称 | 核心内容 |
|---|---|---|
| 1 | 产品 | 搜索、分类、商品列表、详情、加购/询价 |
| 2 | 清单 | 当前项目 BOM、OS 来源清单、勾选/数量/同步状态、去提交 |
| 3 | 订单 | 待办队列、订单列表、报价/审批/付款/物流状态 |
| 4 | 我的 | 企业身份、角色、地址簿、发票抬头、成员入口、联系销售 |

入口策略：

- 微信内分享商品详情时，直接进商品详情；未绑定企业也允许浏览。
- 从 OS/H5 跳转小程序时，携带 `projectId` 或 `handoffId`，进入“清单”并显示项目上下文。
- 从销售/客服发出的链接可直接进入“询价清单”或指定商品。

## 4. 关键体验设计

### 4.1 产品页

手机上的产品页应强调“快速找到型号”，不是展示商城首页。

建议结构：

1. 顶部搜索框：支持型号、品类、关键词。
2. 横向主分类：夹爪、四轴机械臂、六轴机械臂、灵巧手、模组等。
3. 当前筛选摘要：如“夹爪 / 现货 / 夹持力 >= 40N”，点开底部抽屉。
4. 单列商品卡：图片、型号、名称、库存/物料类型、价格或询价、加购按钮。
5. 筛选抽屉：按品类动态展示负载、臂长、行程、夹持力、自由度，不要常驻占屏。

体验细节：

- 商品卡不要做 PC 那种左右密集信息；每张卡只保留购买决策必要信息。
- “定制件/需询价”要直接写明“提交需求后销售报价”，避免用户以为缺价。
- 缺货按钮不要只是 disabled，应给“到货提醒/联系销售”的可行动作。

### 4.2 商品详情

建议内容顺序：

1. 商品图和型号。
2. 名称、价格/询价、库存状态、物料类型。
3. 底部固定 CTA：`加入清单` / `提交询价` / `联系销售`。
4. 规格参数：默认展示 5-8 个关键参数，其余折叠。
5. 兼容附件/相关产品：横向卡片。

小程序不要依赖 hover，也不要把 CTA 放在页面中部。底部操作栏是核心。

### 4.3 方案清单/BOM

这是小程序版最需要重新设计的模块。

建议结构：

1. 顶部项目切换：显示当前项目名、来源（官网选购 / Hitbot OS）、同步状态。
2. 清单分组：标准件、定制件/询价件、参考件。
3. 每行物料：勾选、图片、型号、数量步进器、状态标签、价格/询价说明。
4. 底部汇总栏：已选数量、可下单金额、需询价数量、提交按钮。

业务规则：

- 参考件默认不选中，文案是“参考件，不参与采购”。
- 定制件可选中，但提交动作是“询价/销售承接”，不直接付款。
- OS 来源清单要显示“来自 Hitbot OS 项目”，避免采购不知道这批物料从哪里来。

### 4.4 移动结算

PC 结算有四步：清单、收货、付款/发票、提交。小程序建议分角色处理：

| 角色 | 小程序主动作 | 体验 |
|---|---|---|
| 工程师 | 提交给采购 | 只确认清单、项目备注、采购接收人；不填写付款/发票 |
| 采购 | 提交订单/询价 | 选择地址、付款方式、发票抬头、审批流 |
| 管理员 | 审批/直接提交 | 重点是审批动作和企业设置入口 |

移动端不要一页塞完整表单。建议每一步一个页面或一个沉浸式步骤，并使用底部主按钮推进。

### 4.5 订单中心

订单页首屏不应该是完整订单列表，而应该是“我现在要处理什么”。

建议结构：

1. 行动队列：待审批、待付款、待报价确认、待收货。
2. 最近订单：按状态筛选，默认显示未完成。
3. 订单详情：状态时间线、清单、金额、发票、物流、审批记录。

小程序里订单操作要轻：

- 审批：同意/驳回 + 简短备注。
- 付款：个人支付可走微信支付；对公付款显示付款信息、上传/填写凭证或等待后台确认。
- 报价：查看报价、确认接受、转订单。

### 4.6 我的企业

小程序首版建议做“身份与常用资料”，不要把 PC 的企业管理完整搬进来。

P0：

- 当前公司、角色、联系人。
- 地址簿。
- 发票抬头。
- 联系销售/客服。
- 退出/解绑。

P1：

- 邀请成员。
- 成员列表。
- 简单权限展示。

P2：

- 审批规则配置。
- 企业资料审核流。
- 更复杂的权限矩阵。

## 5. 技术落地建议

### 5.1 推荐方案

已开始新增独立小程序应用：`apps/wechat-miniprogram`，使用 **Taro + React + TypeScript**。

理由：

- 当前 PC 项目是 React/TypeScript，Taro 可以延续 React 心智。
- 小程序需要原生导航、TabBar、登录、支付、分享、客服能力，不能只靠 Next.js 响应式页面解决。
- 业务类型、格式化工具、API client 可以共享；React 组件和 Tailwind 样式不建议强行共享。

可选方案：

| 方案 | 优点 | 风险 |
|---|---|---|
| Taro + React | 与现有技术心智接近，适合共享 TS 类型和部分逻辑 | 仍需写小程序组件和样式，不能复用 Next 组件 |
| 原生微信小程序 + TypeScript | 性能和平台一致性最好 | 与 PC 技术栈割裂，重复开发更多 |
| uni-app | 跨端生态成熟 | 当前项目不是 Vue，团队要接受 Vue 体系 |
| WebView/H5 嵌入 | 最快看到页面 | 体验不像小程序，登录/支付/分享/审核和性能都有成本，不建议作为正式方案 |

### 5.2 仓库结构

建议改成轻量 monorepo：

```text
hitbot-store/
├─ apps/
│  ├─ web/                    # 现有 Next.js 可逐步迁入，或先保留 root
│  └─ wechat-miniprogram/      # 新增 Taro 小程序
├─ packages/
│  ├─ domain/                 # Product / Cart / Procurement 类型与纯函数
│  ├─ api-client/             # API 请求、错误模型、鉴权注入
│  └─ design-tokens/          # 品牌色、字号、间距 token JSON
└─ docs/
```

当前先不搬动现有 Next 项目，只新增：

```text
apps/wechat-miniprogram/
packages/domain/
packages/api-client/
packages/design-tokens/
```

现有 PC 继续在 root 运行，后续再整理。

### 5.3 可共享与不可共享

建议共享：

- `Product`、`CartItem`、`CartProject`、`EnterpriseProfile`、`OrderStatus` 等类型。
- 商品/订单/清单的纯业务规则。
- `formatPrice`、状态文案映射、订单筛选逻辑。
- API client 和错误处理模型。
- 设计 token 的原始值。

不建议共享：

- Next.js 页面和 React Server Components。
- shadcn/Radix 组件。
- Tailwind class 组合。
- PC header/footer、hover 菜单、桌面表格布局。

## 6. API 与后端依赖

当前 PC 端大量依赖 localStorage mock。小程序如果要“功能基本一致”，必须先有服务端数据，否则跨设备、企业账号、OS 项目 BOM 都无法成立。

P0 API：

| 能力 | API 方向 | 说明 |
|---|---|---|
| 登录 | 微信登录 code -> 服务端会话 | 小程序端通过微信登录拿 code，后端换取身份并绑定企业成员 |
| 企业身份 | 当前企业、角色、成员权限 | 决定工程师/采购/管理员可见动作 |
| 商品 | 列表、详情、分类、筛选、库存、价格 | 与 PC 共用 |
| 清单/BOM | 项目列表、清单项、勾选、数量、同步状态 | 替代 `hitbot-cart-v2` localStorage |
| OS handoff | 接收 OS 项目 BOM、状态流转 | 小程序可以承接采购接续 |
| 订单 | 创建、审批、付款状态、物流、详情 | 小程序订单中心核心 |
| 询价 | 提交询价、报价确认 | 定制件必需 |
| 地址/发票 | 企业地址簿、发票抬头 | 移动结算必需 |

支付建议：

- 个人支付/小额支付：可接微信支付。
- 对公付款：小程序应展示付款信息、提交凭证或等待后台确认，不要伪装成即时支付。
- 支付下单必须由后端生成支付参数，小程序只调用支付能力。

## 7. 视觉与交互原则

沿用当前品牌气质：克制、工程化、红黑白为主、少边框、靠颜色和层级表达状态。

小程序需要额外注意：

1. 触控目标不低于 44px。
2. 关键动作固定在底部，不依赖页面中部按钮。
3. 筛选、项目切换、发票/地址选择用底部抽屉或单独选择页。
4. 订单/清单里的长型号、长公司名、长发票抬头必须有截断和详情展开。
5. 空状态要给下一步动作：去选产品、联系销售、绑定企业、查看待办。
6. 加购、提交、审批、付款都要有明确成功反馈和下一步入口。
7. 弱网下清单操作可本地乐观更新，但必须显示同步状态。

## 8. 分阶段计划

### M0：体验方案与原型（约 1 周）

- 小程序 IA、主流程、角色流转图。
- 产品列表、详情、清单、结算、订单、我的高保真。
- API contract 草案。
- 决定 Taro/原生/uni-app 最终技术栈。

### M1：商品与清单 MVP（约 2 周）

- 小程序工程初始化。
- 商品列表、详情、分类筛选。
- 方案清单/BOM：加购、勾选、数量、项目上下文。
- mock API 或最小服务端 API 对接。

### M2：企业身份与提交流程（约 2-3 周）

- 微信登录 + 企业成员绑定。
- 工程师提交给采购。
- 采购提交订单/询价。
- 地址簿、发票抬头基础能力。

### M3：订单行动队列（约 2 周）

- 订单列表和详情。
- 审批、报价确认、付款状态、物流确认。
- 与 PC 端订单状态保持一致。

### M4：发布前打磨（约 1 周）

- 性能、分包、错误态、弱网、埋点。
- 微信小程序审核材料。
- 分享卡片、客服入口、隐私协议。
- 真机回归和灰度发布。

## 9. 主要风险

1. **后端未就绪**：如果仍只有 localStorage，功能无法做到跨端一致。应先定义 API contract。
2. **企业账号绑定复杂**：微信身份、手机号、企业成员、PC 账号之间必须统一，否则小程序会出现“登录了但没有企业权限”的断点。
3. **对公支付不是即时支付**：要把“付款动作”和“付款确认”拆清楚。
4. **OS handoff 来源不清**：采购必须看懂项目名、提交人、来源、清单差异和状态。
5. **范围膨胀**：在线体验 OS 和管理后台不进入小程序范围，避免首版被非采购链路拖慢。
6. **PC 组件不能直接复用**：要共享业务模型，不要强行共享 UI。

---

## 10. 建议下一步

1. 确认小程序首版范围：是否包含真实支付，还是先做到提交订单/询价和对公付款状态。
2. 确认登录绑定方式：微信登录后按手机号绑定企业成员，还是通过企业邀请码/后台开通。
3. 先做 5 张关键原型：产品列表、商品详情、方案清单、提交订单、订单行动队列。
4. 同步拆 API contract，并把 PC mock store 的字段迁移成共享 domain 类型。
